# HOMA · 亚马逊运营工作台

源码主仓库：[JiangYu3761/amazon-ops-agent](https://github.com/JiangYu3761/amazon-ops-agent)。后续开发、代码同步和服务器升级以本仓库的 `main` 分支为准。

以产品型号为主线的运营项目工具。**v0.4仍不是全自动亚马逊运营Agent**；详细功能边界与验证记录见 [需求覆盖表](docs/requirements-coverage.md)，网页“功能覆盖与系统设置”也逐项列明。

新增 API 自动同步与统一经营计算：SP-API 逐日销售／流量、FBA 库存、Ads SP 商品报表只读适配器，持久队列、后台调度、参数版本与来源校验；九板块显示可计算指标及缺失依据。真实店铺授权待配置，SB／SD、实际净利润与售后队列尚未接入，详见 [数据自动化说明](docs/data-automation.md)。

## 开始使用业务工作台

登录后打开「产品总览」查看跨模块待办，或从专业页选择办理类型。经办人填写有效范围、标题和业务对象后，正式草稿会自动写入 PostgreSQL，表单显示保存状态。经办人可手动保存草稿、指定范围、提交审核、登记实际执行和凭证；指定审核人可批准、退回或复核。管理人员分配审核人。点击每页最右侧的原功能标签可继续使用原有产品矩阵、SOP、CSV 导入、月历或系统设置。

- [团队执行手册](docs/运营工作台执行手册.md)逐项列出岗位、输入、办理步骤、字段校验、AI 提示词、下游交付和 79 项原 SOP 的对应关系。
- [可离线搜索的手册](docs/workbench/运营工作台使用手册.html)下载后可在浏览器中打开。
- [验收记录与复现命令](docs/workbench-validation.md)区分真实应用测试、模拟平台响应和仍需授权的店铺验收。

专业表单的“按规则检查”支持无模型密钥运行。“模型起草”使用服务端已配置的 LLM，文案由人员核对。正式业务存入 PostgreSQL。试用本地静态演示时，数据仅保存在该浏览器；完整部署步骤见“运行模式”。

## ERP 业务办理

采购审批、仓库收货与调拨、自发货拆包、售后退货、付款和结算对账在原工作台内办理。总览包含可点击的 ERP 待办与商品经营环比。部署准备、办理入口和逐步试办样例见 [ERP 业务办理与验收](docs/ERP业务办理与验收.md)。

## 当前界面

- 全流程 SOP 事项详情升级为逐阶段审批单，包含业务表单、完整审批链、每阶段人员与计划／预计／实际时间、退回修订、附件及历史快照；入口保留产品和筛选上下文。见 [审批单说明](docs/approval-workflows.md)。

- 新增「流程协作」：可点击流程图、时间/地点/人员、动态填写项目、附件上传、指定人员会签/或签/顺序审核、版本和操作记录。只有流程管理员可配置字段与审核人。首次管理员设置与具体边界见 [流程协作说明](docs/process-collaboration.md)。
- 多产品 × 店铺、合规、Listing、广告、备货、活动、财务、售后、复盘九个板块的进度矩阵。
- 共享79项SOP；清单与看板；按状态、负责人、阶段、关键词筛选。
- 独立“产品交付清单”：四大分类 → 具体工作项与预期交付 → 对应文件链接；按型号查看文件准备情况和阶段状态，支持多个链接、版本历史、缺件筛选与CSV导出。
- 任务自建、责任分配、依赖、文字/链接证据与审批；更改交付要求后旧审批失效。
- 活动月历与任务截止日、成员工作负载、待审批队列。
- 销售/广告/库存/成本CSV：下载模板、先校验、预览有效行和错误行、再提交导入。
- 独立排名类型与曲线、监控参数；采集器尚未接通，明确显示未运行。
- 常驻Agent入口；默认型号+页面+筛选范围；示例使用规则摘要，服务端可配置外部模型。
- 登录后，经营指标由后端统一计算，支持日期范围、公式与输入查看；管理员可在系统设置配置数据源及补货／广告目标参数。SP 广告花费率与全渠道 TACOS、贡献估算与净利润分开说明。

## 运行模式

**静态预览**：无构建依赖。只使用当前浏览器的示例工作空间，顶部一直显示来源。内置的G11、S-CK024和HOMA Loom进度、成员与曲线是示例，不代表实际经营状态。旧浏览器演示数据保留在原存储键，本版使用独立的`homa.ops.workspace.v4`键。

```bash
cd frontend
python3 -m http.server 8080
```

本机单文件体验可通过 `python scripts/build_workbench_demo.py HOMA-demo.html` 生成。下载或复制这个 HTML 后可双击打开，选择“进入本机示例”。Firefox 文件直开并断网时，已逐一打开 17 笔样例和 60 种表单，验证刷新恢复和四种 CSV 模板下载。

Sites打包：`python scripts/build_frontend.py` 生成 `dist/`，不在静态托管内运行Python服务或PostgreSQL。

**完整后端**：FastAPI + PostgreSQL 16。环境依赖安装由Dockerfile完成。

```bash
cp .env.example .env
# 修改数据库密码，并同步DATABASE_URL。不要提交.env。
docker compose up --build -d
```

Web：`http://localhost:8080`；API文档：`http://localhost:8000/docs`。数据库只在Compose内部网络开放。API 启动会按版本升级现有数据卷，迁移成功后才开始服务。手工维护时也可执行 `sh scripts/migrate.sh`。新建产品生成79项SOP；已有旧模板可点击“补全新版SOP”，按旧任务映射保留证据和状态，不替换整库。

流程协作已提供个人登录、管理员配置权限和指定人员填写/审核。旧任务配置接口也要求管理员登录；已启用协作的节点通过流程接口处理。其他经营 API 尚未具备完整访问隔离；团队正式使用前仍应放在已有的私有访问网关后。系统升级沿用流程管理员的登录权限。具体权限边界见上面的流程协作说明。

## Agent页面范围

默认只传当前型号、当前页面及其任务筛选，不传其他页面数据。切换页面或型号切换对话范围；对话ID与产品绑定，拒绝跨产品复用。

显式范围：`@全局`、`@流程`、`@交付清单`（或`@资料`）、`@店铺`、`@页面`、`@广告`、`@库存`、`@活动`、`@利润`、`@售后`、`@合规`、`@排名`、`@建议`、`@导入`、`@团队`。

服务端环境变量：

```env
LLM_API_BASE=https://api.openai.com/v1
LLM_API_KEY=
LLM_MODEL=
```

密钥不放在网页中。兼容Chat Completions接口，不保证所有模型都接受相同参数。外部模型与Amazon API尚未实机验收。

## 产品交付清单

选择型号后，按“店铺运营、Listing与素材、广告运营、供应链与交付”四类查看同一套79项SOP。表格前三列固定为大分类、具体工作项/预期交付、对应文件链接；后面显示准备情况、工作阶段状态与负责人。原九个专业工作台继续保留。

一项工作可以关联多个现有文件或文件夹，记录名称、版本、准备状态与备注。文件“已准备”是人工确认，不代表内容已审核或阶段已完成；更新交付会使任务原审批失效并重新验收，历史链接保留但不计入当前准备情况。模板中的预期文件名是交付建议，并非已存在的文件。

此功能保存文件索引，不上传、读取或更改原平台的文件权限。静态模式只存当前浏览器；服务端模式需执行`db/006_product_documents.sql`，通过PostgreSQL共享索引。Agent默认只读取当前型号和当前清单筛选后的记录，不读取链接中的文件正文。

## 数据导入

标准模板位于 `frontend/templates/`，不是Amazon原始报表自动映射器。日期使用`YYYY-MM-DD`、UTF-8编码、文件≤10 MB。必填值不可空，成本不得默认为0。币种、SKU、ASIN需与产品一致；同一业务键重复导入更新原行。

| 类型 | 必填列 |
|---|---|
| 销售 | date, sku, units_ordered, ordered_revenue |
| 广告 | date, campaign_name, impressions, clicks, spend, sales, orders |
| 库存 | date, sku, fulfillable, reserved, inbound, unsellable |
| 成本 | date, sku, product_cost, first_mile_cost, fba_fee, referral_fee, other_cost |

模板有示例行，导入真实数据前应替换。用户先看预校验结果，再决定提交有效行。后端会再次校验；产品或币种不一致会拒绝本批文件。销售额不等于回款，广告销售不加到总销售额里；退款、税费、仓储与期间费用未接全前不显示净利润。

## 系统升级

页面顶部和 SOP 审批单顶部均有「检查并升级」。已登录管理员点击一次后，系统自动检查 GitHub；没有更新则显示“已是最新版”，有更新则自动备份、构建、迁移、重启并检查运行状态。无需额外升级口令或再次确认。未登录时使用现有个人登录，登录成功后继续；普通成员不能发起升级，接口也验证管理员身份。

完整 Docker Compose 部署默认包含升级工作进程（`UPDATE_ENABLED=true`）。从项目根目录启动，项目宿主机绝对路径默认采用 `${PWD}`，不要求固定安装目录；Docker daemon 位于其他机器时应由部署人员在安装阶段设置 `APP_HOST_DIR`。使用公开主仓库的 HTTPS origin：`https://github.com/JiangYu3761/amazon-ops-agent.git`，无需 Deploy Key。只接受 `main` 的快进更新和干净的程序目录。

弹窗显示当前版本、目标版本、检查时间和执行进度。API 重启期间自动恢复查询；重复点击或关闭后重开会继续查看同一任务，不重复部署。工作进程离线、网络失败或构建失败会显示明确结果，静态预览会说明未连接升级服务。

升级前保存数据库、上传附件与初始化配置码备份，以及旧服务镜像。失败时恢复旧代码与镜像；备份和内部日志保存在忽略提交的 `backups/`，普通状态接口不公开路径和原始日志。数据库备份保留供恢复使用，不自动逆向执行已提交的数据库迁移；涉及不兼容数据库结构的版本仍需先做部署演练。

`updater`只从固定主仓库读取代码，挂载 Docker socket 以更新同一套服务，不能作为公共业务端口暴露。升级工作进程心跳、请求锁和中断恢复会防止离线排队、重复升级与中断后卡住。

## 广告决策复盘

登录并选择产品，在「广告运营 → 效果复核」办理。原广告单的经办人可以在变更已经批准、尚未执行时登记预期、基线、观察期及对照证据。登记执行凭证后发起复盘，由单据指定的另一位审核人签署结论。缺少事前计划的历史单可以补作回溯观察。到期时分别核对实际执行、归因是否成熟、经营护栏、干扰和实际对照。数据更正可重开原单，旧结论保留在办理历史中。

「周期复盘」按产品业务日查看日、周、月及历史截止日。对同一店铺、广告账户、对象及动作，系统在登记下一笔事前计划时重新核对前案。投放调整申请的对象写作 `profile:123/target:456`，或者使用 `campaign`、`adgroup`、`keyword` 层级；预算复验按 campaign 识别，竞价按 adgroup、keyword 或 target 识别，暂停支持这四种层级。否词和新增定向等缺少足够稳定的身份时继续人工办理。只有前案证据符合条件时，才可明确选择其签署版本进行后续小范围复验。

复盘数据使用 PostgreSQL 迁移 `025_ads_decision_reviews.sql` 和 `026_ad_review_feedback.sql`。应用升级沿用现有迁移入口。办理单记录运营提交的外部执行证明，接入商家广告账户后的 API 回读和实验仍需各自验证。

在已配置 `WORKBENCH_TEST_PG` 的本机 PostgreSQL 测试环境，可运行 `WORKBENCH_BROWSER_SCRIPT=scripts/check_ads_reviews.cjs python scripts/check_workbench.py`。它建立并清理独立测试库，浏览器中演练登记、签署、重开、周期指标及下次复验。
